# LESSONS — retro-earned constraints

Cumulative across milestones. Only `/retro` writes here.

## Audience tags

Every lesson carries one or more audience tags. `/orchestrate` and `/loop-plan` deliver each consumer only its own slice, so a lesson reaches the stage that can act on it and nowhere else:

- `[planning]` — `/loop-plan`: task decomposition, packet contents, what to verify before a packet states it as fact.
- `[builder]` — `builder` and `implementer`: how to write the code and its tests.
- `[reviewer]` — `code-reviewer`: what to look for in a diff.
- `[docs]` — `docs-writer`: what must be true of a durable document (a decision record, a doc comment, a journal entry).
- `[testing]` — `test-runner`: how this project's suite misreports — a runner that exits 0 on nothing, a cache that fakes a pass, a prerequisite whose failure reads like a code bug.
- `[verifier]` — `verifier`: what the running app does that its tests don't show, and what this project's stack makes hard to observe.
- `[security]` — `security-auditor`: the shapes this codebase gets wrong, and which of its trust boundaries are worth re-reading every unit.

A lesson with no tag is a bug in the entry, not a lesson for everyone. Add the tags it needs.

A lesson may carry several tags. It is written **once**, and each stage receives only the entries tagged for it — never a copy. Splitting this file per audience would duplicate the majority of it, and the first thing to drift would be the lesson below about facts that drift.

## Seeded lessons

Entries marked `[seed]` were inherited when this project adopted the loop, not earned here. They are real — each one comes from a specific failure in the project the loop was built in — but they have not been tested against *this* project's stack. Two consequences:

- Treat them as active constraints, not suggestions. They describe how agents fail, which is stack-independent.
- If one turns out not to apply here, `/retro` retires it with a one-line reason. Retiring a seed is a normal outcome, not a failure.

Where a seeded lesson names a specific tool, the **rule** is the lesson and the tool is an example — substitute this stack's equivalent (see `loop/PROFILE.md`).

**Not every audience has a seeded lesson, and that is correct.** `[security]` has none: no security defect has yet been earned in a project the loop ran, and inventing one to fill the slot would violate the rule every entry here is held to — a lesson names a specific failure that actually happened. An empty slice costs nothing at spawn time. `/retro` fills it the first time this project teaches it something.

## Retired lessons

A lesson is **retired** when its content becomes permanent instruction text in a skill or agent file, or when a seed proves inapplicable here. `/retro` moves it to `loop/lessons-archive.md` as a one-line pointer. It is never deleted outright: the pointer is what stops a future `/retro` from re-deriving the same lesson and re-adding it.

The archive exists so that job costs nothing at spawn time. A retired lesson has no audience — its content is either already permanent instruction text or does not apply here — so leaving it in this file made every agent pay to read something none of them could act on, forever. `/retro` reads the archive; nothing else does.

## Seed (inherited on adoption)

### Planning

- `[seed] [planning]` **Verify framework internals during planning, not during implementation — the same class of claim costs a build failure at one stage and nothing at the other.** The source project ran this experiment twice in one milestone with opposite results. One task discovered at build time that a scheduler wrapped its target in a package-private class, so a direct type check never matched — two implementations compiled and failed before decompiling settled it. Its sibling task verified four equivalent claims *while the packet was being written*, landed them as stated facts, and cost zero respins. When a packet's approach depends on how a framework, driver, or database behaves internally, probe it while writing the packet — the answer becomes a constraint the builder designs around instead of a wall it hits. A verified internal is also what lets you pick an implementation *shape* the guard can observe.
- `[seed] [planning]` **A work item's stated deliverables are a hypothesis, not a spec — re-derive its scope before planning from it.** This holds hardest for items the loop filed itself. Two such items in the source project were both materially wrong despite being written by agents with full context: one named two files needing a fix when there were four; the other's named fix would have degraded real request handling far outside its stated target, manufacturing exactly the failures its own tests existed to catch. Both were caught only because planning re-read the code instead of transcribing the item. Verify every count by counting, and check whether the named fix reaches beyond its stated target, before a packet inherits it.
- `[seed] [planning]` **When a verification is judged untestable, name the layer that judgement applies to and check whether another layer can reach it.** The source project's grilling correctly concluded that a dependency-down scenario could not be proven from the in-process test suite, because the app cannot boot without that dependency — then stopped, and the task settled for a weaker assertion with honest documentation about what it did not prove. The verification was trivial one layer out: stopping the dependency's container against a running app produced the real healthy-to-unhealthy transition, and closed a second verification line that had been handed to the user as manual work. "Untestable" almost always means "untestable at the layer I was thinking about." Before accepting it, ask whether the container, the compose stack, or a live process can observe what an in-process test cannot.

### Building

- `[seed] [planning] [builder]` **Verify every factual claim in your task packet against the code before relying on it, and report discrepancies instead of working around them.** The source project's packets were wrong four times in one milestone: a claimed test shape exercised a path another component made unreachable; a count of 21 enum cases was actually 22 (the arithmetic omitted the case the task existed to add); an exploit trace had a step a lock made impossible; a list of two offenders was actually three. Every one was caught by an agent that re-derived the claim rather than trusting it, and every one would otherwise have shipped a wrong doc comment, a wrong decision record, or an incomplete fix. Line numbers especially: they go stale the moment an earlier task edits the file.
- `[seed] [planning] [builder]` **A claim about how a dependency behaves internally is a hypothesis until you observe it — and reading your own code cannot settle it.** This was the dominant failure mode of one whole milestone, five times over, and every resolution came from direct observation rather than reasoning. The techniques that settled them are cheap and available in every stack: decompile or read the dependency's own source, ask the database for its actual plan or lock state, print identity hashes of injected objects, log what the framework actually constructed. Use them before writing a doc comment, a decision record, or an assertion that depends on the answer. This is distinct from verifying packet claims against your own code: these claims are unfalsifiable from your source and require probing the dependency itself.
- `[seed] [builder] [reviewer]` **A guard only counts if it can observe the failure it claims to catch — prove it by breaking the thing and watching the guard fire.** This failed three ways in one milestone. A doc comment named a case needing special handling and a later milestone shipped that exact case without it, because a comment cannot fail a build. A test asserting an exact set so that drift would fail loudly missed a change entirely, because the change moved the behaviour and touched neither side of the assertion — an exact-match assertion is silent when both sides stay still. A third guard was unreachable dead code until an unrelated reordering made it live. By contrast, that milestone's two strongest deliverables each ran their regression test against the *unfixed* code first and reported the failure output. Do that whenever you add a guard.
- `[seed] [builder] [reviewer]` **Before writing a test for concurrent or timing-dependent behaviour, check that its parameters permit the outcome it asserts.** One test used 3-item requests over a 5-item pool, where any two requests must overlap, so only one thread could ever win — making it a costlier duplicate of the test beside it until the pool widened. Another would have made its central assertion trivially true in a single pass, because only one thread ever reached the code path being counted; it needed two phases to become a real race. State in the test's documentation what it does *not* cover. Assertions that cannot fail are worse than absent ones, because they read as coverage.
- `[seed] [builder]` **Fix-first ordering matters most during revert-and-restore sequences, and the dangerous half-applied tree is the one that still passes.** An agent was killed by a session limit immediately after announcing it would revert its instrumentation, having already reverted the tests and not yet restored them. That left production code in the tree with zero coverage — and crucially the suite still passed, so nothing signalled a problem, and a commit there would have shipped untested code whose whole design turned on one branch. Never hold tests reverted while their production code stands: restore them before doing anything else, including before writing up findings. When resuming an interrupted agent, require it to state its established findings *first*, before touching code, so a second interruption cannot lose them. And when any agent reports what it was about to do, read the tree rather than trusting the report.
- `[seed] [planning] [builder]` **Sequence long tasks so the tree stays coherent at every step, and finish the fix and its regression test before the documentation.** Three agent runs in one milestone were killed mid-task by session limits and one stalled on a watchdog, twice leaving a task unverified. Work that lands fix-first survives an interruption; a half-applied refactor does not.

### Tools, fixtures and blame

- `[seed] [builder] [testing] [verifier] [reviewer]` **When a tool looks broken, suspect your own invocation before you suspect the tool — and prove which it is before editing anything.** On the loop's first real adoption, an agent fed the audit hook a hand-escaped JSON payload, saw nothing written, correctly identified this as the hook's documented silent-failure mode, and edited the hook to fix it. The hook was fine: the *fixture* was malformed JSON, and the shell it was blaming handled the case natively. The agent caught this only because it went back to check whether its own edit had been necessary, then reverted — one step from permanently forking a machinery file that must stay identical across every project that adopts it. Three rules follow. Build fixtures with a real parser rather than by hand-escaping quotes. When a tool and your input disagree, isolate by changing the input first, because that is the half you control. And when you have already made the edit, verify it was needed against the unmodified tool before you keep it — a fix for a bug that never existed reads exactly like a fix that worked.

### Documents and numbers

- `[seed] [planning] [builder] [reviewer] [docs]` **A fact worth stating twice will drift; when you correct one instance, grep for every other and fix them in the same change.** One milestone hit this four times. A reasoning error lived in two decision records *and* a task packet, and fixing both records still left the contradicting version sitting in a config comment and in the loop's own plan file — where it would have been re-read at the start of the next run and propagated onward. A README claimed 117 tests against an actual 129. A baseline figure was stale by five commits, and an agent rationalized the resulting mismatch as "which aligns with the new test class" rather than flagging that it did not add up. Two consequences: after any correction, search the whole repo for the old claim before calling it done (the loop's own append-only journal is the deliberate exception — never rewrite history there); and when an agent reports a number alongside a story about why the number is fine, verify the number, not the story.
- `[seed] [planning] [reviewer] [docs]` **Mark the epistemic status of every number that reaches a durable document — "measured" and "estimated" must not read identically.** A decision record stated a worst-case timing budget as settled fact, and that figure propagated into a doc comment and a container healthcheck comment before review caught it. The underlying check had proved something narrower than what the number claimed. The failure mode is specific and nasty: a document that outlives the conversation that qualified it, read later as a verified constraint by someone tuning against it. When a figure is derived rather than measured, say so in the same sentence and name what would settle it.
